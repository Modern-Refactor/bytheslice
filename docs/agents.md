# 🍕 Agent Roster

Every ByTheSlice subagent in one table, in plain English. ByTheSlice ships 29 subagents, and every one is a registered plugin agent: type `@bytheslice:<name>` in any Claude Code session to aim one at something directly, or just run the skills and let them dispatch. Registration means each agent's model tier, effort level, and tool allowlist (when its file declares one; an agent without a `tools:` list gets every tool) are enforced by the platform, not just suggested.

Bold rows mark the skill each group of agents belongs to.

| Agent | Kitchen character | What it does |
|---|---|---|
| **🍕 /setup-shop** | | |
| scripts, no agents | | `scripts/detect-ci.js` checks whether the standard CI safety nets (test workflows, pre-push hook, PR template) exist and lists what is missing, with a lean app needing a smaller set. `scripts/write-config.js` turns your setup answers into the `bytheslice.config.json` settings file and never overwrites one without asking. |
| **🍕 /create-menu** | | |
| `brief-analyzer` | Bree | Reads your project brief and spots what is vague or missing, then proposes a short list of questions to ask you before the PRD gets written. |
| `prd-reviewer` | Prue | Final quality check on the finished PRD: compares it against your original materials and returns pass or revise. |
| **🍕 /cook-pizzas** | | |
| `stage-planner` | Stan | Plans the stages, always read-only, in three modes. `full` (/cook-pizzas) reads the PRD and proposes how to cut the project into Pies and Slices, sized to the PRD (a small app gets a few small pies; 20 to 30 slices is a ceiling for big apps, never a target), then shows you the roadmap for approval before anything is written; for each pie with a user-facing flow it also proposes 3 to 7 user steps, each owned by one slice, and a step no slice owns shows up as a warning in that same approval. `extend` (/special-order) sizes up a mid-project feature request: one slice or several, what type, what it depends on, roughly how much work. `options` weighs 2 to 3 design approaches (minimal change, clean architecture, pragmatic balance) with a recommendation; an unattended run picks pragmatic balance and records why in the stage file. Plans only, writes nothing. |
| `rules-assembler` | Russ | Builds the project rules file (CLAUDE.md or AGENTS.md) by layering house rules, your own imports, and design-system rules in the right priority order. |
| `phased-plan-writer` | Phil | Writes the detailed plan file for one feature slice. Many copies run in parallel, one per slice, and it also handles new slices added later by /special-order. Its `db-schema` mode writes the plan for the database-schema slice, adapted to your database tooling (Supabase, Prisma, Drizzle), and only runs if your project has a database. A frontend or full-stack slice that owns a user-flow step gets exactly one user-outcome Exit line, which `slice-tester` checks end to end. |
| `master-checklist-synthesizer` | Max | Collects what every plan writer produced and assembles the single master checklist that drives all future work, including each pie's short User flow list. Pure bookkeeping, no creative decisions. |
| **🍕 /set-display-case** | | |
| scripts, no agents | | `scripts/token-check.js` checks a design bundle exported from claude.ai/design (`bundle`) and is the design-system gatekeeper that refuses to call the system done until every required token category is filled in (`complete`). It reads Tailwind v4 `@theme` blocks and can check the approved draft before any file exists. |
| `library-route-scaffolder` | Lars | Builds the hidden `/library` page, an in-app showroom where every UI component is previewed before it ships, and keeps it out of your site's navigation and search. |
| `token-expander` | Tia | If you have no design bundle, this turns a written brand description into a full set of design tokens and shows you the values for approval before writing files. |
| **🍕 /final-quality-check** | | |
| `scaffold-discovery` | Sky | Fingerprints the repo first: package manager, framework, monorepo or not, existing CI workflows, database presence, and which end-to-end testing setup fits (usually Playwright). Everyone downstream reads its report. |
| `scaffold-writer` | Wren | Fits out the repo one block at a time, dispatched once per block so each gets its own review: `e2e` (end-to-end framework, standard scripts, starter tests), `workflows` (GitHub Actions for CI, E2E, design-system compliance and schema drift), `husky` (the pre-push hook), `lint` (rules that catch hardcoded colors and spacing, `.gitignore` tidy-up), `branch-protection` (a one-time script that locks main). Skips what already exists and never overwrites an existing rule. |
| *(script)* | Ollie | `scripts/run-gates.js` runs the entire gate suite locally (lint, types, tests, E2E, visual) in the background before the first push and reports a short summary, with full logs on disk. No agent. |
| `a11y-discovery-runner` | Ally | Runs a scoped shadscan accessibility scan to surface issues no other gate catches, throws out anything pointing at your `/library` mockups, and hands back the rest as leads to check by hand. It never blocks, never scores you, and never fixes anything. |
| **🍕 /open-the-shop** | | |
| scripts, no agents | | `scripts/env-inventory.js` finds every `.env.example` and lists the keys your project expects (`scan`), lists the secrets your CI workflows reference (`secrets`), renders the manual checklist grouped by service with provisioning links (`checklist`), and confirms your `.env.local` files hold real, non-placeholder values (`verify`). It never prints a secret value. |
| **🍕 /sell-slice** | | |
| `code-explorer` | Pip | Thorough, read-only exploration in three modes. `stage-recon` maps which files, symbols, and callers the slice will touch, so the build plan is grounded in the real codebase. `slice-scope` picks the next slice off the master checklist, defines pass/fail acceptance tests for it, and proposes the exact checklist update (suggests, never edits); it runs in the same dispatch as stage-recon. `feature-trace` (/special-order) returns the 5 to 10 key files, entry points, conventions and risks for a requested feature before the questions start. |
| `rules-loader` | Bea | Loads the project rules file and `bytheslice.config.json`, and hands back the resolved settings the rest of the pipeline should obey. |
| `implementer` | Ren | The builder. Writes the code and its unit tests for one checklist item, updates the DB schema first when needed, and declares everything it produced in a build manifest. Runs the quick checks while coding and before each commit, never grades its own work, and hands its changed files to the conductor, which does all the committing. |
| `code-reviewer` | Quinn | One pass over the builder's work, covering the plan and the craft: was the checklist item actually delivered with no scope creep and following project conventions, and are the types, tests, edge cases, security smells and schema-before-queries sound. Leaves out only minor nits it is less than 80 percent sure of: every blocker and major is reported with its score, and a failed gate is never filtered out. Cannot write files, by construction. |
| `slice-tester` | Tay | The independent QA. Gets only the build manifest and the slice's definition of done (never the builder's chatter), then actually exercises the feature: clicks through the UI at every viewport or round-trips real data, runs a blocking keyboard, focus and contrast pass on UI, and reports evidence per claim (screenshots only at 768 and 1280). |
| `slice-verifier` | Inez | Runs the full local suite once at the end of the slice (lint, types, build, tests, E2E, design-token grep, CI integrity; a lean app runs just its one smoke E2E, and a ship-once build runs exactly the commands its CI workflows run) and cross-checks the diff to catch anything the manifest under-declared. After a fix it re-runs only the checks that fix could change and says which and why. Its tools let it read and run commands but not edit files. |
| `fix-attempter` | Fitz | When a check fails, makes the smallest possible fix for that one failure. No refactors, no scope growth, no commits (the conductor commits). At most 3 fix loops per slice before it asks you, and it stops sooner if the same failure comes back unchanged. |
| `debug-instrumenter` | Dee | If the first fix did not take, adds temporary tagged logging around the failure so the next fix attempt has real data. The tags are stripped once everything is green. |
| `ui-fix-attempter` | Uma | The same fixer on the bigger model, called in only when the fix targets come from the UI reviewer below (`ui-reviewer`, in either mode). Fixes the component or the data boundary, never the worst-case test data. |
| **🍕 /sell-slice frontend pipeline** | | |
| `ux-layout-designer` | Lyle | Two serial steps in one dispatch: researches how best-in-class products solve this screen and writes a short UX spec with the chosen patterns and a few visual references, then reads that spec, writes the route files and page shells (the skeleton of the screen) and appends the breakpoint plan to it, leaving the components' inner workings to others. |
| `ui-builder` | Kit | Covers as much of the UI as possible with ready-made shadcn blocks before any custom code, and reports exactly what percent is covered and where the gaps are. When a gap is keyboard-heavy (menus, dialogs, comboboxes, tables), it checks up to 3 installed libraries through Context7 and writes binding component rules so nobody hand-rolls what a dependency already ships. It then hand-builds only the gaps, using design tokens exclusively: no raw colors, fonts, or spacing values. |
| `library-entry-writer` | Libby | Puts every new or visually changed component in the `/library` showroom with all its variants and states, so you approve the look before it touches production routes. Its tools stop at files, read-only shell commands and the shadcn registry, and it never stages or commits. |
| `state-illustrator` | Lu | Sweeps the UI for missing loading skeletons, empty states, error states, and success confirmations, and fills in the gaps. On screens that show lists, tables or cards it also adds a dev-only `?data=demo|worst|empty|one|many` switch with realistic test data. |
| `ui-reviewer` | Celine | The difficult customer and the food critic, in two modes, reporting only and never editing code. `break` loads every data-driven screen with the worst realistic data (very long names, emails with no break points, one-letter names, empty and 1,000-row lists, non-Latin text, emoji), measures what breaks at desktop, tablet and phone widths, and writes a report with screenshots (built on Emil Kowalski's break-ui skill, copied in at a pinned commit). `critique` scores a few main screens against Nielsen's 10 usability heuristics, ranks the problems and asks you the open questions, using the impeccable critique (pinned copy, run without its downloadable binary); it runs at the library gate for new composite blocks, once per pie before the PR, and in `/inspect-display`. Only minor design findings (P2 and P3) below 80 percent confidence are dropped; serious ones (P0 and P1) are always reported with their score, and measured accessibility and design-system failures are never dropped. |
| **🍕 /box-it-up** | | |
| `ci-fix-attempter` | Dex | When the PR's CI goes red, reads the failing checks and makes the smallest fix that turns them green; `/box-it-up` commits and pushes it. At most 3 rounds per PR, and it stops at the first identical repeat. Never weakens tests to pass. |
| **🍕 /inspect-display** | | |
| `platform-walker` | Wally | Drives a real browser through every route of your running app, screenshots everything, reads the console, and returns a ranked list of what looks broken, stubbed, or empty. |
| **🍕 /special-order** | | |
| `code-explorer`, `stage-planner`, `phased-plan-writer` | Pip, Stan, Phil | No agents of its own: it dispatches these three, in their `feature-trace`, `extend` / `options` and incremental modes (described under /sell-slice and /cook-pizzas above). |
| **🍕 /pizza-party** | | |
| `stand-in-operator` | (none) | Stands in for you during an unattended `/pizza-party` run. When a business question comes up that your interview answers did not settle (a feature cut, who may see what, what data to keep), it decides it the way you would, picking the choice that is cheapest to undo and shipping anything with outside exposure switched off, and the run lists every such call at the end with how to change it. It runs on the top `fable` tier but is called rarely: only for those questions, a batch at a time, with a per-run budget. Read-only; it never asks you, never approves deleting anything shared, and never makes up a credential. |
| **🍕 /close-shop** | | |
| `retrospective-reviewer` | Rhea | Reads the project's history (logs, commits, PRs, escalations, and the Pass ledger's metrics when the mod ran) and identifies recurring friction the plugin itself caused, then proposes a patch for each improvement. Barred from modifying /close-shop itself. |

## Scene roles and extra instances

The [kitchen roster](../skills/dashboard/kitchen.html) groups characters into Opening crew, Test kitchen, Display case, The line, The pass, Back door and Review board. Those scene divisions may differ from the owning skill groups in the table above.

- **Chef Nico** is the orchestrator, the lead session that keeps the line moving. It is not a separately registered plugin agent.
- **Sal** represents `/box-it-up` at the front window. It is a skill character rather than another registered agent.
- **Dom** is `implementer#2`, the second simultaneous instance of the registered `implementer` role. Ren is the first instance. Dom does not increase the unique registered-agent count.
- **Ezra** is the `expediter` scene role who pins and splits tickets in the demo kitchen. It is not a registered plugin agent: its live work (picking the next slice) belongs to `code-explorer`, which is Pip.
- **Paz** is the `review-scribe` scene role at the close-shop review board. It is not a registered plugin agent: the plugin no longer ships a proposal drafter.
- **Ollie** is the `oven-tender` scene role who tends the oven. It is not a registered plugin agent: the full local gates are `scripts/run-gates.js` now.
- **Pia** is the `plater` scene helper that collects slices and plates pies. It is not a registered plugin agent.
- **Base crew and town crew.** While a pie is open in live mode, Dom works the line, Ollie tends the oven and Sal minds the window on ambient duty, with Chef Nico leading; an agent that is actually running wears a gold work tag. The rest of the named crew live in town, in flats above the Main Street shops, until their agent starts, then run in to their station and walk back out when it finishes. The People sheet's Crew and Town tabs open a profile card for any of them.
- Additional simultaneous plugin instances use numbered helpers in the matching division, such as `line helper 1`. Unknown plugin roles use line helpers. Non-plugin agents appear as numbered **Temp** helpers at the pass, preserving their actual agent type in the role description.
